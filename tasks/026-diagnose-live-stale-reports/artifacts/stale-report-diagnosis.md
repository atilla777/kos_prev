# Stale Report Diagnosis

Date: 2026-09-27

## Retained Reproduction

Task 025 retained the authoritative state before and after four rejected live
standard-subagent reports. A local OpenCode permission log retained the matching
submitted command lines. Comparing those records identifies `owner_id` as the
only divergent fence field:

| Scenario | Authoritative owner | Submitted owner | Claim version | Step |
| --- | --- | --- | --- | --- |
| Development task 2 | `kos-session-5ed...` | `kos-session-b00...` | `2` / `2` | `implement` / `implement` |
| Fix task 3 | `kos-session-1e0...` | `kos-session-06b...` | `4` / `4` | `document` / `document` |
| Custom task 5 | `kos-session-8de...` | newly generated by `session-id` | `3` / `3` | `standard_probe` / `standard_probe` |
| Custom task 5 retry | `kos-session-8de...` | `kos-session-696...` | `3` / `3` | `standard_probe` / `standard_probe` |

Owner values are shortened because full values add no diagnostic value. They
are terminal non-secret coordination identifiers. Task 025's retained
`agent-launches.json` records the authoritative task 2 fence at lines 400-411,
task 3 at lines 533-544, and task 5 at lines 414-467. Its selected subagent
events at lines 179-207 and 269-277 bind those unchanged states to the four
rejections. The local command log showed that each rejected standard agent used
the correct current version and step but a fresh owner.

## Boundary

The ambiguous instruction was in `skills/kos-cli/SKILL.md`: the common template
listed `Owner: session-id` without limiting owner creation to the scheduler.
`skills/kos-step/SKILL.md` asked executors to supply identity and fence but did
not name the exact context fields. Standard agents interpreted those together as
permission to generate a new owner immediately before reporting.

The CLI and server forwarded and rejected that owner correctly. No context
selection, workflow transition, or claim-version mismatch occurred.

## Correction

Step executors now reread context immediately before reporting and take
`task.owner_id`, `task.claim_version`, and `task.current_step` together from that
response. They explicitly never call `session-id` or use
`artifacts[].accepted_claim_version` for reports. Scheduler owner creation,
server-side fencing, and bounded unchanged-state recovery are unchanged.
